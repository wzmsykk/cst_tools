# CST的WinWrap加载与宿主初始化路径

2026-11-03。针对独立NoUI出现评估到期的后续核查。**此前PoC未复现CST宿主的初始化链，所以只能证明开发示例token在本轮独立宿主中未初始化成功，不能证明CST运行环境不可用。**

## 当前证据

|核查对象|已确认|不能推导|
|---|---|---|
|安装目录AMD64|含WB9ENT64.OCX、wwb9_64.dll及OCX侧car manifest；WinWrap版本9.21.027|文件位于相同目录不自动等于其他宿主具备CST相同初始化条件|
|侧car manifest|声明WinWrap类型库和BasicIdeCtl COM类的映射；此前已核查具体CLSID|manifest是加载/绑定配置，不是许可目录或可用于独立初始化的授权接口|
|modeler_AMD64.exe与DE exe|本轮PE普通/延迟导入表未直接列WB9ENT64.OCX或wwb9_64.dll；嵌入manifest主要是Windows Common Controls依赖|未能从这两个表确定完整WinWrap加载/初始化顺序；不据此断言CST不使用这些组件|
|v9 Initialize帮助|参数是SerialNumber；示例开发token仅用于已安装开发环境|没有文档依据将其替换为CST安装路径或某个.lic路径|
|现有CST外部接口|归属明确的3D对象RunScript可运行固定驱动；语言文档提供MacroCheckThis|尚未实测MacroCheckThis在该宿主内的上下文和诊断，不承诺外部可取得内部NoUI实例|

本轮只检查PE导入名称、XML RT_MANIFEST及公开帮助，不反汇编初始化代码、不读取许可文件或嵌入激活材料。文件及manifest hash与导入名称见[证据](../knowledge-base/cst-winwrap-loading-20261103.json)。未启动CST、未再运行Initialize、未改注册表。

## 必须分开的三个问题

1. **找到同版本引擎**：本机安装发现及文件hash已能完成。
2. **加载组件及类型库**：独立免注册NoUI已通过受控激活测试，正常关闭已验。类型库映射问题与授权初始化问题不能混为一谈。
3. **复用宿主初始化条件**：本项目还没有经过核实、可独立调用的CST授权初始化接口；这不是一个已经查明的“许可目录”配置项。不要把开发示例token路径的失败写成对CST宿主路径的验证结论。

WinWrap当前官网的[证书文档](https://www.winwrap.com/web2/license-certs)说明v10存在针对特定应用/服务器的宿主授权。它只能作为区分宿主与开发环境的参考，不能直接套用为CST所带v9的证书格式、搜索目录或合同结论。v9仍以随安装帮助和供应商明确支持的接口为依据。

## 方案修订

- 若复用CST本身的初始化环境，应通过本项目已有、归属已核实的CST会话运行固定MacroCheckThis驱动，由CST宿主保持其正常初始化方式。不导出宿主凭据，也不把CST许可文件搬到Python旁边。
- 为降低CST过重的成本，后续可评估一次启动、同一固定驱动内批量检查所有样本，并与受限离线规则分层。此前二次RunScript有本机未执行记录，因此不直接设计为反复RunScript调用的常驻服务。具体批量驱动/无求解退出仍需真实校准，不提前宣布可用。
- 若要求完全不启动CST，必须进一步确认供应商支持的独立NoUI初始化方式及本机使用条件；目前不添加未经核实的license_path选项。没有该条件时将独立NoUI标记为不可用，保留ANTLR辅助预检及受限生成规则。
- 不能以重命名宿主、提取CST内嵌凭据、复制许可材料或绕开Initialize的底层CodeUnit调用来构造“复用授权”。本方案需要的是受支持的接口，而非使测试绕过初始化检查。

本次没有完成真实CST宿主授权路径跟踪。下一步若继续要求不启动CST，只能推进供应商文档/支持接口核实；若允许少量宿主校准，则用一次无求解副本同时检查正常/反例、上下文、诊断与标准退出。现有本轮“不启动CST”约束仍保持，未擅自启动。
