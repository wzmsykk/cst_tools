# CST 内存保护

## 正常轮换

Manager 默认每个 Worker 最多完成 6 次任务（原为 10 次），可通过 `max_jobs_per_worker` 调整，例如 5 或 8。轮换发生在完成结果读取、确认快照与 Ack 之后；先标准关闭，再重建。顺序 HOM 保留已确认快照接力，标准批量任务保持从基准工程开始的语义。

## 异常内存监测

`WorkerConfig.memory_guard` 使用 `MemoryGuardPolicy`；默认开启，每 30 秒采样框架启动的 CST 根进程及其子进程。Windows 使用 private bytes，总和不重复计算共享 DLL 页；其他平台使用 RSS。依赖 `psutil>=5.9`。

只有以下条件同时成立才认为需要资源保护，并不据此断言根因一定是内存泄漏：

- 进程树内存至少 8 GiB，超过物理内存 90%，且至少为本轮初始采样的 4 倍。
- 以上高占用持续至少 10 分钟。
- CST 日志字节数至少 10 分钟未变化，且未收到 Completion。

采样失败或占用回落会打断持续高占用证据；日志变化重新计算无进展时长。日志不变化不等于 Solver 一定死锁，阈值应按工程规模调整。合理的大模型若一开始就使用很高内存而没有四倍增长，不触发本保护；这不是机器全局 OOM 保证。多个独立 Worker 或用户工程造成的总内存压力也不能由单个进程树判断覆盖。

## 清理与恢复

触发时先保存故障诊断并申请标准停止，沿用 120 秒退出门限。只有标准退出失败，才调用已有紧急进程树清理，仅指向当前 Popen 所属 CST，不按进程名全局结束。当前任务报告 `CST_MEMORY_GUARD`，不发布成功结果；由 Manager 原有重试、已确认快照和 HOM 检查点逻辑处理。重试用尽时保留失败/未确认区间，不承诺自动恢复所有任务。

没有求解总时限；高 CPU 或 40 分钟以上求解本身不会触发保护。紧急清理可能丢失当前未确认计算，仅保留此前确认结果。`enabled=False` 可关闭自动内存保护；当前未增加 GUI 阈值编辑器。

## 验证边界

使用假进程与模拟采样验证持续门限、进展/回落重置、访问失败、Completion 优先、标准退出优先及紧急清理分支。不为测试制造真实系统内存耗尽；真实 CST 异常内存与快照续跑仍需独立集成验收。已有发布压缩包未包含本次修改，需重新打包。
