## 1. 问题与现状

当前GUI、ApplicationService、Backend、扫描算法、Manager和Python Worker处在同一Python进程。
QThread与ThreadPoolExecutor只隔离执行线程，不能隔离进程崩溃。正常关闭窗口会请求停止并等待收尾；
任务管理器结束Python、Qt原生崩溃或系统异常不会保证执行closeEvent、finally或退出时保存。

CST由subprocess启动，是外部进程。Python死亡后CST可能继续计算，但不能保证继续派发、接收或安全退出。
当前VBA完成任务后先保存快照、写Completion，再等待Ack；没有Python控制器和停止请求时可能长期等待。
CREATE_NEW_PROCESS_GROUP不是“独立后台服务已验收”的证据。

已有恢复资产包括：

- 求解前登记pending，处理后保存模式、完成/空/失败区间和覆盖账本的HOM检查点。
- 经过路径、大小、哈希检查的已确认工程快照。
- received/acknowledged及algorithm_adopted阶段记录、任务协议、会话恢复回执。
- 运行日志、摘要和索引；这些用于诊断，不替代成功证据。

恢复上限是最后一个可验证持久化阶段，不是崩溃瞬间内存。扫描区间恢复不等于CST求解器内部迭代续算。
当前仅后处理恢复、完成但未接收等时间窗口尚未全部闭合，不能保证不重算。
近期完整离线回归出现Qt原生退出，具体根因未定；这是隔离需求的风险背景，不是CST故障证据。

## 2. 目标与非目标

目标：GUI死亡不影响运行；Runner死亡后先对账、不盲目重复计算；任何恢复都能说明阶段、证据及下一步。

第一版不做远程控制、集群调度、Windows服务、消息队列、自动重启续算、活跃CST热接管、
求解器内部断点续算或新的Python/VBA ABI。保留默认单Worker、HOM窄区间nmodes=1、参数表达式和历史持久性边界。

为后续远程/分布式预留Controller/节点执行边界、可序列化任务、逻辑工件引用及实例身份，
详见[远程与分布式扩展设计](remote-distributed-execution-design.md)。此预留不扩大第一版本机实施范围。

## 3. 架构与职责

```text
GUI进程：配置草稿、状态显示、命令确认
    │ 本机控制接口
Runner进程：配置快照、生命周期、项目所有权、检查点、日志
    └─ 现有Backend → 算法 → Manager → Python Worker
                                          │ 现有文件协议
                                       CST / VBA
```

一个项目一个Runner，一个Runner同时一轮运行。多个GUI可查看，同一时刻只有一个GUI拥有修改控制权。
Runner不依赖Qt、不引用GUI控件，不依靠GUI的stdin/stdout连接存活；GUI启动时发现已有Runner则连接，不另起竞争者。
Windows启动与句柄继承、控制台/Job对象影响须进程级验收，不能只凭启动flag认定分离成功。

|对象|职责|
|---|---|
|GUI|编辑草稿、确认操作、展示；不直接创建Manager/CST或修改活动配置|
|Runner|验证和记录命令，冻结配置，控制Backend，持有所有权|
|Backend/Manager|保留调度、停止、恢复和Worker回收|
|Python Worker|保留协议、结果核对、Ack与CST归属判断|
|CST/VBA|计算、复杂后处理、快照和协议发布|
|持久化资产|恢复依据；状态快照和事件显示可由证据重建|

ApplicationService可作为迁移入口，但不把全部同步方法机械映射为RPC；拆分配置草稿与不可变运行请求。

## 4. 拟议控制协议

采用仅监听本机回环地址的HTTP/JSON，小范围固定操作，不暴露任意Python方法、文件执行或shell。
随机认证令牌限制本用户读取，不进入URL、普通日志、发布包；请求体大小、连接与请求读取均有界。
不启用跨站调用，校验认证及请求来源边界。本机接口不是局域网服务。

|操作|语义|
|---|---|
|读取状态|权威运行状态、阶段、覆盖、任务、会话安全状态和首错误|
|开始运行|一次提交完整配置快照及源工程身份|
|继续运行|指定项目与检查点，核验并对账后恢复|
|请求停止|持久化停止意图，迅速返回已接收，不阻塞等待求解返回|
|恢复会话|运行既有归属核验、标准停止和结果对账|
|读取事件|按游标分页，限量读取|
|退出Runner|只在无活动任务且归属会话已安全闭合时完成|

修改命令携带request_id；针对运行的命令必须携带run_id，过期运行命令拒绝。
相同request_id和内容返回既有处理结果；同ID不同内容拒绝。先持久化意图再执行副作用。
接收、执行、完成分开；HTTP成功不能解释为CST成功。GUI请求超时表示结果未知，查询原request_id，不能另造ID重复启动。
幂等覆盖进程重启，不能仅用内存缓存。恢复中未完成命令先对账，不能机械重放。
控制处理与长任务执行分离；阻塞Backend操作不得堵住状态查询和停止意图接收。

## 5. 状态与并发

三组状态独立：

- GUI连接：已连接、重连中、不可达。
- 运行：空闲、准备中、运行中、停止中、完成、中断、失败、需要恢复。
- CST会话安全：已确认关闭、仍活跃、未知、恢复失败。

GUI断开不改运行状态；Runner不可达不能显示为已停止。暂停仍是协作停止形成恢复点，不是冻结Solver迭代。
快照带实例身份和递增状态版本；GUI丢弃旧版本。事件带实例/运行身份和游标，游标失效则重新获取快照。
命令串行校验状态和控制权，长任务独立执行；所有实际计算副作用仍由唯一控制器发起。

## 6. 所有权和多窗口

两层所有权分别处理：项目Runner所有权防多控制器，现有Backend运行锁防计算/恢复写入冲突。
配置草稿不写活动项目；Runner取得必要保护后校验、冻结、保存运行配置。锁顺序固定为Runner所有权后运行锁。
活动运行期间不能切换项目或CST版本；GUI可查看其他项目，但不能因此重定向原Runner。

现有ProjectRunLock主要按PID判断存活，迁移需补主机、用户、进程创建时间和实例身份。
访问被拒绝或身份无法核实应视为未知，不是已死；心跳过期不允许直接抢锁。
所有权获取/废弃回收必须有原子互斥，不能依靠读文件后无保护unlink来承诺并发安全。
令牌仅用于核对持有者，不能代替排他锁或证明旧控制器已停止。
多GUI控制权可释放/明确转移；客户端失联不停止计算，控制权转换不改变Runner所有权。
跨主机共享项目抢占不在第一版支持范围；网络盘相关语义单独验收。

## 7. 结果事务和恢复

沿用现有RunStore、检查点、received及快照，避免再建重复任务数据库。

```text
提交意图落盘 → 发布任务 → CST完成及产物
→ 校验并保存received → Ack/会话确认
→ 算法检查点提交 → algorithm_adopted
```

跨Python、CST和文件系统不承诺单一原子事务或exactly-once求解。采用阶段可重入、身份核对、先对账后行动。

|崩溃位置|恢复要求|
|---|---|
|意图已写、任务未发布|确认无外部执行后继续提交|
|任务已发布、无完成|检查归属进程及协议，不立即重算|
|完成未接收|核对完成身份、产物和后处理要求，能接收则补接收|
|已接收、Ack未完成|恢复协议闭合，不能只凭接收记录继续派任务|
|已接收、算法未采用|核对执行指纹与快照，复用结果提交检查点|
|检查点已提交、采用标记未写|以检查点任务身份对账补标记，不再次推进覆盖|
|多个冲突结果|阻断并报告，不按时间随意选最新|
|结果/快照缺失或哈希改变|不认定成功，保留诊断和未完成区间|

覆盖以区间账本、失败/pending缺口及快照为准，不以最高找到频率替代。
需要审计检查点是否记录足够任务身份，尤其空区间结果的采用身份；不足时做最小版本化扩展。
工程.cst与同名场结果目录分别登记；单独工程快照不能证明三维场可读。
原子替换不等于断电持久性，关键写入需明确flush/fsync策略；第一版目标为进程崩溃恢复，断电另验收。

## 8. 退出和异常策略

GUI运行中关闭提供取消、仅关闭界面后台继续、安全停止后退出；默认取消。
Runner仅由明确命令退出，停止失败保留诊断接口与恢复状态，不自动消失。
阻塞Rebuild/Solver/单算子不能即时抢占；启动/预处理/Worker注册阶段必须保留停止意图，返回后不得继续下一阶段。
GUI重连不能因超时判定任务失败；接口失联应展示未知及最后观测时间。

Runner自身死亡时：确认旧实例已死 → 核实锁及CST归属 → 既有协议标准停止/确认死会话
→ 对账完成/接收/检查点 → 明确恢复命令续跑。第一版不热接管仍在计算的CST派发新任务。
活跃CST不会因GUI或Runner崩溃而保证自动退出；需要恢复控制器执行标准收尾。不得用强杀作为常规收尾。
系统关机、断电、磁盘满、访问拒绝分别报告，不保证全部可恢复；关键持久化失败停止新派发，不伪造安全完成。

## 9. 目录与日志

拟议新增项目control目录，既有运行日志及结果位置保留：

```text
项目/control/runner.json      # 实例、端点、协议版本；不是存活证据
项目/control/commands/       # 命令及处理结果
项目/control/status.json     # 可重建状态快照
项目/logs/index.md
项目/logs/时间_用途_短ID/      # 原有run.json、summary.md、双日志
原有HOM检查点、结果、Worker协议与恢复回执
```

认证凭据独立受保护存放，具体位置实施时确定。临时运行目录不能随GUI退出清理。
Runner单独写完整日志；GUI写自身诊断并按事件游标增量显示，避免重复写入同一应用日志。
GUI读取有界、分页、有背压，丢显示事件不丢持久化事实；工程和大场文件仅返回映射/摘要，不经状态接口反复传输。
清理只针对确认结束且可再生的数据，保留恢复所需快照、接收记录、掩码、协议和轻量证据。

## 11. 验收矩阵

- 假Worker下分别在初始化、预处理、求解、后处理、收尾期间终止GUI；Runner继续且可重连。
- 同项目并发启动两个GUI/Runner、同请求重发、响应丢失、旧run_id停止请求、控制权转移。
- 在第7节各事务窗口终止假Runner再恢复，核对任务调用次数、结果和区间覆盖，不能只看退出码。
- PID复用、访问拒绝、损坏元数据、错误令牌、不同用户CST及共享路径别名。
- 磁盘满、写入失败、协议损坏、快照/场文件丢失、多个候选结果，均不能误判成功。
- 长日志与慢GUI不阻塞Runner，事件游标断档能恢复，GUI状态过期明确标识。
- 发布包用独立进程启动、关闭GUI、重连、标准停止；验证句柄、工作目录和解释器环境。
- 真实CST仅在明确授权后串行副本测试，不改原工程，不用强杀CST代替停止。

进程级隔离必须通过真实进程中断验证，仅在线程中抛异常不够。现有离线测试数字不作为本设计验收。
