# CST场后处理效率验收

## 结论

对于本次两mode公共点重叠计算，**CST原生HDF5导出＋Python明显优于VBA逐点累计**，不是Python计算快就推断全流程快，而是实际计入了结果树切换、取场导出、读盘、复数组转换和计算。该结论不包含CST原生编译场算子；下方补充验收已证明同一原生网格的DotProduct远快于VBA循环，不能笼统推荐所有计算都导出Python。

110,592点、两mode、三次重复中位数：VBA路线3.645秒，原生HDF5路线1.609秒，约2.26倍加速。VBA手写CSV路线24.556秒，不适合作为正式实现。小点数优势不稳健，不能宣称所有规模Python都更快。

## 条件与范围

- CST2022；已有cell=30求解快照；两mode E场六个实/虚分量。未运行Solver、修改参数或Rebuild。
- 原快照SHA256未变。CST打开已有快照后执行SaveAs(include_results=True)创建验收副本，不手动复制伴随目录。仅复制.cst不能读取已求解E场；这不改变新求解任务只复制.cst的规则。
- 在项目坐标 x/y=-10至10、z=-50至50 的固定区域均匀中心采样，分别12³、24³、48³点。位置相同、等权累计，不是完整计算域的体积积分验收，也未验证该区域是否足以区分整个模族。
- 每档3次，固定执行顺序，无清除文件系统缓存。VBA Timer有毫秒级量化；Python perf_counter计时。读盘主要是热缓存，不代表冷盘/网络存储性能；未做独立峰值内存验收。

## 第二轮：原生Result3D点乘

证据 `D:/work/cst_tools/artifacts/field-efficiency-51b42d87/report.json`。打开同一cell=30快照后带结果另存，直接从两mode结果树获取原生场文件，用Result3D加载；仍未运行求解器。

### 共轭规则

构造单点向量，仅X分量非零，a=1+i、b=2+3i：

- 直接DotProduct返回-1+5i，即普通乘积ab，不是Hermitian内积。
- 显式对a调用Conjugate再DotProduct返回5+i，符合a* b。

因此复场重叠必须显式取共轭。DotProduct会修改调用对象，后续范数或其他配对不能复用已被点乘覆盖的对象。

### 同原生网格性能与一致性

两场均有927,060个原生数组采样项，等于本模型92,706个四面体的10倍；是场采样项数量，不是网格单元数。

| 路线/阶段 | 3次中位秒 |
|---|---:|
|两场Result3D初始加载|0.03125|
|原生共轭＋点乘＋两范数，含范数所需额外对象加载|0.71875|
|原生路线总计|0.75000|
|VBA参考加载、GetArray及数组复制|4.48438|
|VBA参考逐点累计|6.42969|
|VBA参考完整路线|10.90625|

完整路线约14.5倍差距；不同原生数组与前一轮公共ROI点集不是同一种计算，禁止用0.75秒与公共点HDF5的1.609秒直接排出优劣。两者只能分别证明各自语义下的效率。

原生及同索引VBA参考的最大范数尺度误差6.90e-10，满足本探针1e-6容差。该误差归一化不保证极小交叉项的相对误差同样小。合成复数语义检查和真实数组一致性检查均通过。

整场未加体积权重的数组平方和不能解释为储能；不因覆盖所有数组项就称其为正确体积积分。只有同一原生网格、采样顺序一致的字段可使用此探针；长度相等也不足以证明来自不同工程的两个网格坐标一致。

### 更新后的选型

1. 同一次求解、同原生网格的简单点乘/诊断：优先CST原生算子，仅输出小矩阵，避免VBA循环。
2. 跨网格的COMSOL式场重叠：仍需公共采样或可靠插值及积分权重，HDF5＋Python是已测可用路线。
3. 下一候选是公共点批量采样→Result3D.SetArray→原生DotProduct，只传小矩阵。它可以避免VBA循环和场文件导出，但尚未验收性能和数值正确性。
4. 正确体积加权、跨工程插值及峰值内存仍待独立验收；不改变现有逐mode逐积分线R/Q物理后处理。
