## A1 / P1：过期控制权不能由GUI申请

**认可。** `csttool/runner.py` 的 `snapshot`直接返回owner_client，`command`的claim分支才按monotonic时间判断10秒租期。
`GUI/runner_controller.py`的poll仅比较owner_client判只读，而_command拒绝只读情况下的所有操作；现有GUI也没有独立申请控制权入口。
服务器允许过期claim并不证明GUI有可达路径。

影响：旧GUI崩溃后，新GUI可以查看活动运行，但不能发停止/恢复/新运行等修改命令。后台本身不一定故障，却会形成UI操作死锁。

拟修复：

- snapshot提供控制租约是否有效、剩余时长/是否可申请，以及控制权修订身份；不要让GUI根据另一进程的monotonic绝对时间推算。
- GUI提供“申请控制权”操作，在只读时可达；其他修改仍拒绝。过期或空闲不表示已自动取得控制权。
- claim在服务端同一锁内重新核对并授予。旧客户端迟到心跳不能无条件复活已失效/已转移租约。
- 不改变项目Runner/计算所有权，不以接管GUI控制权为理由重新派任务或终止CST。

补充门禁：旧GUI持权时崩溃→租期过期→新GUI申请并停止同一run；有效租约内拒绝其他GUI；两个GUI同时申请仅一个成功；
旧心跳/旧claim重发不能夺回已转移控制权。需GUI端到端验证，不能只测Runner.command允许过期claim。

## A2 / P1：启动响应丢失导致排队停止丢失

**认可。** RunnerController.poll在finished_operation为start的异常分支清除stop_after_start；
_command没有在GUI侧保留稳定请求ID、内容与返回run_id映射，start响应结果本身也被丢弃后改为观察状态。
服务端持久去重虽存在，但客户端未用它完成该故障窗口的对账。

影响：服务端已启动运行、GUI请求安全停止后退出，但启动响应超时时，重连看到RUNNING却不再发stop，计算继续、窗口持续等待。
“错误发生所以清除停止标记”不是安全恢复策略；也不能用重连时的当前run_id直接补停，避免误停其他新运行。

拟修复：

- 派发前保留完整待处理命令（稳定request_id、project_id/本地连接代次、客户端身份及内容摘要），停止意图绑定该启动请求。
- 超时保留“启动结果未知、停止待确认”，通过命令查询对账原启动请求与其run_id；不创建新ID重发start。
- 针对查询时尚未存在/迟到启动的竞态，服务端支持按原启动请求登记取消/停止意图，并与启动接受在同一锁内判定。
  未接受的启动可被取消墓碑阻止后续迟到执行；已接受的启动只停止其对应run；已结束的启动只回报终态，不作用于当前其他运行。
- 仅在绑定目标已取消、已标准停止或已终结并核验后清除意图。未能联系服务端不能宣称停止完成。
- 若要求GUI再次崩溃后仍保留“停止后退出”意图，须持久化客户端命令关联或把意图交给Runner确认；不能只保留内存布尔值。

补充门禁：真实本机HTTP层在服务端持久接受并开始执行后丢弃/延迟start响应；同时点击停止或安全退出；重连后仅同一run被停止、启动次数为1。
另测未到达、迟到到达、结果已完成、控制器重启、项目切换和另一运行已开始。查询“未找到”不能单独证明旧请求永不会到达。

证据级别：本轮已合成Future超时→重连RUNNING的状态机复现；尚未做HTTP丢包/响应延迟注入，也未用真实CST复现。

## A3 / P2：同窗口切换项目后不启动新Runner

**认可。** RunnerBackend.select_project_directory替换client但未重置Controller.instance；_observe以instance是否None决定launch。
连接过A项目后切换尚无Runner的B项目，B会被当作已有连接的故障恢复，使用launch=False。
现有status.project比较可阻止部分旧成功响应，但未覆盖旧异常、排队命令及A→B→A的同路径旧响应。

影响：新项目无法正常从该窗口启动Runner，可能一直显示未知；旧游标、只读状态、运行ID及未完成停止意图还可能污染新项目交互。

拟修复：建立按项目绑定的连接上下文及递增generation。切换时重置实例/运行ID、游标、连接与控制状态，清理或明确保留原项目命令关联。
旧控制权通过捕获的旧client释放，不通过新的backend.client释放；旧任务不因切换被自动停止。
所有成功、异常与命令回调均核对generation和项目身份；不能只比较路径。新项目允许首次启动，原项目失联仍禁止自动重启。

补充门禁：同窗口A已连接→B无Runner可正常启动；A旧响应/旧异常晚到不污染B；A→B→A时第一代A响应被忽略；
旧控制权正确释放、不把旧stop发给新项目；活动运行切换按明确策略断开/拒绝，不自动取消原运行。

## A4 / P2：超长JSONL行卡住后续回放

**认可。** Runner.events读取65537字节，若未遇换行就退回原位置；没有区别“文件末尾尚未写完”和“完整行超过读取上限”。
即使超长行已完整写入，每轮仍返回原cursor，后续正常事件不可达。

影响：GUI日志从该处永久停滞，隐藏后续错误和收尾证据；不必然阻塞CST计算，但破坏诊断可见性。

拟修复：采用有界分块解析和显式游标状态（文件/运行代次、offset、是否正在跳过超长行），
为超长记录返回明确的截断/跳过提示及原始文件位置，跨请求推进至下一完整记录。普通未完成尾行仍等待补全。
原始.log/JSONL不删除、不截断；不将部分JSON拼成虚假的完整业务事件，也不使用无界readline读取巨型行。
游标协议如改变须更新版本与客户端；轮转/换运行时不能沿用旧行的continuation状态。

补充门禁：阈值上下边界、70KB行后正常事件、多MB跨批次行、UTF-8多字节分界、尾行后补换行、损坏行、日志轮转。
验证单请求内存/扫描预算有界，存在可读后续记录时游标最终推进；诊断失败不能把计算状态错误地改成已失败/已停止。

## M1：配置草稿接口与执行接口混合

**认可，为维护性问题，优先级低于A1/A2，不等同已发生CST重复计算。**
RunnerBackend通过抛异常别名模拟prepare/execute/stop/recover，get_recovery_sessions空列表与is_recovery_required=False又不表示真实后台事实，
仅能满足runtime_checkable结构检查，不能满足执行后端语义。为获取默认设置实例化HomScanAlgorithm也引入不必要的算法依赖。

拟修复：提取无执行副作用的配置模型/默认值与校验；拆分配置草稿、执行控制端口、状态DTO。
生产GUI只依赖客户端控制端口，进程内Backend供Runner/CLI和显式测试使用；去掉伪执行方法与假恢复值。
不为此引入服务框架或机械RPC镜像。保持配置表达式及新运行/续跑语义，迁移相关测试而非长期维持两个生产GUI后端。

补充门禁：草稿构造不创建算法/Backend/CST；运行命令可JSON往返；恢复事实只来自Runner快照；
配置校验前后端一致；旧假后端测试改为显式注入，不靠虚假Protocol方法兜底。
