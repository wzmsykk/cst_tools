# CST 私有工程格式的分析流程

本章记录本项目如何从真实 `.cst` 样本出发，逐步建立可供参数发现、工程对比和 HOM 自动化使用的知识。这里描述的是**针对已观察样本的工程研究流程**，不是 CST 厂商发布的文件格式规范。能读取某个成员，不等于 CST 会接受对它的写回；能找到结果文件，也不等于该结果属于当前求解任务。

## 1. 从需求反推要认识的状态

最初的需求不是完整反编译 `.cst`，而是回答几个具体问题：不启动 CST 能否读取参数及表达式？工程内已有何种求解设置和 Result Template？两个工程或两个子工程到底改了什么？运行后能否直接读取后处理结果？哪些修改仍必须经 CST 自身执行？

因此先建立三层边界：

| 层次 | 目标 | 证据要求 |
|---|---|---|
| 静态盘点 | 列出成员、参数、历史、设置、模板 | 多样本可重复读取；长度和校验值正确 |
| 语义判断 | 解释某个成员代表什么、与哪个子工程关联 | 文件内容、CST 界面/官方接口和前后差分相互印证 |
| 改动与执行 | 修改工程后继续求解、得到可信结果 | 工作副本上的 Open → Rebuild/Solve → Save → Reopen 与结果对照 |

静态读取可以减少旧 VB 参数预处理，但不能自动跨越到“离线修改一切设置”或“删除运行时后处理”。

## 2. 建立样本矩阵，而不是从一个文件推断规范

分析同时覆盖不同年代、不同结构的工程：WTC 2020/2022、Pillbox 2015/2020、TM020，以及 Enlarged/HOM 复合工程。普通工程主要用于确认参数、HISTORY LIST、求解设置和模板的常见位置；复合工程用于暴露 `SP/<name>/Model/...` 命名空间和大型压缩成员的边界。

每个样本应记录来源、CST 版本、SHA-256、文件大小、成员数、是否有参数、是否含子工程、能否由目标 CST 打开。样本对照必须允许“合法缺失”：例如 Pillbox 2015 的参数表为空，并不意味着容器解析失败。对某个版本有效的路径或偏移，也不应不经测试推广到其他版本。

## 3. 先证明容器读取，再读取业务成员

观察发现，当前 `.cst` 样本的外层与 ZIP 相似，但部分头签名为 `DE`，局部头还有厂商布局差异。初版读取器曾在整个字节流中搜索 `DE 03 04`。它能处理较小样本，却在 Enlarged/HOM 中把压缩 payload 内偶然相同的字节序列当作真实文件头，最终造成错误边界和 Deflate 失败。

修复思路是从 EOCD 定位中央目录，逐条读取中央目录记录，再按记录的 local-header offset、压缩长度和文件名定位数据；解压后核对未压缩长度及 CRC，并拒绝重复名称、越界或目录计数不一致。这样成员列表不再依赖“在压缩数据里碰巧找到了什么”。这是一个典型教训：**小样本可读，只证明解析器碰巧适合小样本，不证明容器协议已经理解完整。**

容器层验证通过后，才按成员路径解释内容。当前重点包括 `Model/Parameters.json`、`Model/3D/Model.mod`、`Model/simulationproperties.json`、`Model/Model.prj` 和 `Model/3D/*.r0d/*.r1d`。未知二进制成员先记录名称、大小和哈希，不凭扩展名臆测内部物理语义。

## 4. 逐成员建立语义，并保留不确定性

参数 JSON 可提供名称、表达式、求值结果和描述，因此参数发现不再需要启动 CST 运行旧 VB 脚本。但表达式是 CST 语言的一部分；Python 的 AST 白名单求值只能处理已覆盖的子集，未知函数或依赖必须保持未解析，不能猜值。

`Model.mod` 可按历史步骤标记拆分为标题、注释和代码块，适合审计与版本差异展示。不过注释不是永久 ID；步骤改名、移动或重复时，自动对齐可能呈现“删除＋新增”，仍应保留原文供人工核对。`Model.prj` 的样本则显示 `[Key]` 后跟下一行值，单纯按 `key=value` 解析会漏掉 Mesh Type 等信息；解析规则必须由真实样本校正。

结果文件的区分尤其重要：`.cst` 内的 `.r0d/.r1d` 是含设置表和 VBA 源码的 Result Template 定义，不是最终物理值；运行目录的 `.rd0` 才是本项目已验证的部分 0D 标量结果来源。即使模板文件内容相同，也不能仅凭此证明它在 CST 中已注册并成功执行；即使 `.rd0` 存在，也要核对完成时机、任务身份、单位、模式号和参数状态。

## 5. 将“一个文件”改为“多个 ProjectScope”

Enlarged/HOM 表明，一个 `.cst` 可包含根工程 `Model/...` 和多个 `SP/<name>/Model/...` 子工程。每个 scope 可能有自己的参数、建模历史、求解设置、模板和结果。于是解析、盘点、指纹与比较 API 都必须显式接受 `root` 或 `SP/<name>`；逻辑键应含 scope，不能只按 `Frequency (Mode 1)` 这样的局部名称匹配。

当前 `cst_version` 已能枚举 scope，并逐 scope 读取参数、设置和模板；比较接口可报告两文件中同名 scope 的差异，以及新增或缺失的 scope。GUI 也允许选择同文件内两个工程或外部 `.cst` 的工程。这里的模型指纹是“所选模型相关成员发生变化”的证据，不等同于数学意义上的几何完全相同或物理结果等价。

## 6. 用受控差分检验修改假设

理解一个设置如何保存，最可靠的方法是保留基线副本，在 CST 中**只改变一个因素**（例如频率下限、模式数、Mesh 或一项模板设置），再保存并比较前后成员的哈希与可读字段。随后重开工程，确认界面和官方接口报告的设置与文件差异一致。一次改变多项设置会让因果关系难以辨认。

对离线写回，原则更严格：永不原地覆盖源工程；尽量保留未修改成员的原始字节，只替换目标成员并修补索引；写出后检查成员清单及非目标哈希，再由目标 CST 版本执行打开、重建或求解、保存、重新打开和关键结果回归。正在运行的 Warm 工程不能从外部直接改文件，因为 CST 内存状态、缓存和 Mesh 复用并不会因此自动同步。

## 7. 以真实 CST Gate 决定可用边界

私有格式分析最终服务于自动化，但不能代替 CST 行为验证。当前较稳妥的职责划分是：Python 只读盘点工程、读取已验证的原生文本结果、比较工程身份与任务状态；CST 负责应用运行时参数、Rebuild、求解、必要的复杂场后处理及标准 Save/Quit。固定且预先定义的结果可优先走原生结果读取；任意运行时 R/Q 积分路径仍可能需要 CST 内部后处理能力。

每一条新能力都要有对应 Gate：指定 CST 版本和样本、受控工程副本、预期设置、结果值与单位、完成标记、退出码及无残留 UI/进程。真实小样本通过，也不能自动推出复杂 HOM 全频段已找全；近邻或简并模式仍需单独验证。

## 8. 当前结论与后续原则

本项目已经证明 `.cst` 不是只能经 GUI 访问的完全黑盒：参数、历史、部分设置和模板可以离线盘点，多工程范围可以区分并比较。同时，它仍是私有且随版本和工程类型变化的格式。未解释的成员、未经 CST 证实的写回，以及仅凭文件存在推断结果有效，都应继续标记为待验证。

后续分析沿用同一链条：**明确问题 → 选代表样本 → 只读容器验证 → 成员分类 → 单变量差分 → CST 打开/求解验证 → 记录证据等级 → 才进入正式自动化。**记录失败样本、旧假设被推翻的原因和适用版本，与记录成功路径同样重要。

## 9. 针对以上问题实际的工作流程

实际工作不从“请 AI 直接扫完 HOM”开始，而是把每个不确定点变成一个可验证的小任务。一次新工程或新 CST 版本的接入按以下顺序进行：

1. **由使用者定义目标与基线。** 明确待扫频段、单位、预期的 Q 类型、R/Q 积分轴及路径、边界条件、Mesh 收敛要求，并提供一个已由人工核对的模式及其后处理值。没有这些定义，程序即使导出数字也无法判断是否答对问题。
2. **冻结输入并制作工作副本。** 记录源 `.cst` 的路径、CST 版本和 SHA-256；所有探索、预处理和求解只使用副本。先检查是否为复合工程，列出 `root` 和各 `SP/<name>`，明确本次实际求解的 scope，不把其他子工程的同名结果混入。
3. **只读盘点，形成待验证清单。** 离线读取参数及表达式、HISTORY LIST、仿真设置、Mesh、模板与已有结果路径。输出“已观察到什么、缺少什么、哪些字段语义尚不确定”，而不是直接据此修改工程。若容器验证、CRC 或必需成员失败，立即停止本轮分析。
4. **单变量实验确定 CST 的真实行为。** 依次只改一个设置，在 CST 中保存副本，比较修改前后的成员和界面状态。例如先确认 `fmin` 是否真正绑定求解器，再验证 `nmodes`、Mesh 和模板定义。实验记录包含输入、操作、前后 diff、CST 重开结果及是否使旧结果失效；没有通过的假设不得进入正式自动化。
5. **用小算例建立执行协议。** 先在 Pillbox 等可快速核对的工程上执行一个窄窗口、一个模式：确认求解成功、后处理属于该模式、结果文件已完整落盘，随后标准 Save/Quit。空窗口、求解失败、后处理失败与退出失败分别注入或观察，不能统一当成“没有找到模式”。
6. **先假 Worker，后真实 CST。** 假 Worker 覆盖密集模式、空窗口、重复频率、异常中断和恢复，验证扫描算法与检查点；真实 CST Gate 再核对关键物理值、Mesh 收敛、文件时序和进程生命周期。只在小范围 Gate 通过后扩大频段，完整 HOM 找全必须另有全频段验收。
7. **每个结果附上可追溯身份。** 保存源工程指纹、prepared 工程指纹、scope、CST 版本、频段、参数、Mesh、后处理定义、任务/模式号和结果文件。只有求解完成、结果读取成功且身份一致时才将该窗口写入检查点；中断时从最后一个确认快照恢复。
8. **把发现回写知识库。** 每次遇到不一致，都记录样本、复现步骤、预期与实际、解决方法和适用版本；同步修订测试和功能边界。若官方文档、文件内部字段与 CST 实际行为冲突，以可复现的真实 CST Gate 为当前实现依据，同时保留冲突记录。

### HOM 实现方案如何进入这一流程

前述步骤建立了可信的工程输入和 CST 操作边界；HOM 扫描本身还需要一条明确的执行链，而不是“把频段交给求解器，循环直到得到足够多模式”：

1. **工程准备阶段。** 从源 `.cst` 创建独立 prepared 副本，验证目标工程 scope、CST 版本和必需 Result Template 能力；将 `fmin/fmax/nmodes` 与求解设置绑定，固定 Mesh 或先执行可选的 Mesh 收敛分析。Mesh 和后处理定义在正式扫描前冻结；运行后通过 `Update Params` 再改变积分设置会使结果失效。缺失模板或 Profile 能力必须在第一轮求解前报告。
2. **单窗口任务阶段。** Manager 只派发当前窄窗口，常规 `nmodes=1`。Warm Worker 在同一 CST 会话中应用本轮频率参数、Rebuild、执行本征模求解、完成已定义模板及必要的运行时复杂后处理，并在结果 Save/Flush 后发布 Completion。Python 收到与本任务匹配的 Completion 才读取 `.rd0` 或运行时结果、确认 Ack；不以“文件出现”或局部日志百分比作为任务完成标志。
3. **结果判定与频段推进。** 接受一个模式前，验证 Mode 1、频率落在本轮区间、各后处理值有限且结果名不重复。找到频率 `f` 后从 `f` 加微小容差继续，继承初始窗口宽度但不超过 50 MHz；空窗口则从原上边界推进。空窗口不是失败；多模意外返回、后处理缺失或重复已接受频率则不是正常空窗口，必须显式报错。不能再使用固定 0.1 MHz 向上取整推进，以免跨过近邻模式。
4. **后处理路由。** 对工程中已预定义、语义一致的固定结果，优先读取原生 `.rd0`；任意 X/Y/Z 轴或运行时自定义积分位置的 R/Q 等，保留 CST 内部的 `EigenResult_Complex`/VBA 能力。`.r0d/.r1d` 只用于预检模板定义，不当成结果。频率、Q、R/Q、Shunt Impedance、Total Loss 等值必须与同一次求解、同一模式和声明的积分设置关联。
5. **提交与续跑。** 每轮命中、判空或失败后原子更新 checkpoint 和 CSV，记录区间、结果、失败原因及最后确认的工程快照。HOM 顺序任务显式允许同一 Worker 槽用成功任务的快照接力；未确认任务的临时副本不能提升为恢复点。恢复前校验 manifest、prepared SHA-256、CST 后端、扫描策略、Mesh 和后处理指纹；不一致即拒绝混跑。用户停止先阻止派发新任务，让正在求解的区间到安全点，再经 Stop Request/Ack、Save/Quit 收口；普通恢复不自动强杀仍存活的 CST。
6. **完成判据。** 到达终点、没有未解决失败区间、所有结果可追溯且 CST 标准退出，只构成工程流程完成。物理上的“找全”仍需人工窄区间基线和目标频段真实 CST Gate 验证；严格同频简并模式无法仅靠单模式右移证明枚举完整，需要专门的局部多模探测。

实现顺序也因此明确：先用假 Worker 验证区间推进与异常分类，再用 Pillbox 验证协议和安全退出，最后在目标 HOM 工程上逐步扩大频段。已有十模式异常恢复 Gate 不能替代复杂工程 500–1000 MHz 全频段找全验收。算法细节和当前已验证范围分别见 [HOM 窄区间单模式扫描算法](./hom-scan-algorithm.md) 与 [当前状态与实施路线](./current-status.md)。

这个流程的关键停机条件是：**物理定义不清、成员解析不可信、设置是否生效无法证明、结果身份不一致，或 CST 不能标准退出时，不启动下一轮正式求解。**冷启动案例中，示例参数文件虽然写着 `fmin/fmax/nmodes`，但无法证明它们已应用到 CST，也未明确 Q 与 R/Q 定义，因此合理的动作是停在求解前，而不是退化为鼠标代点并声称完成计算。
